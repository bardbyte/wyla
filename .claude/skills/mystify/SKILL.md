name: mystify
description: Sanitize a repository for publication by scrubbing employer-specific and personal references (internal product names, company names, team acronyms, "paste back" / "check on work laptop" style notes, internal hostnames, ticket IDs) and every trace of Claude or any other coding agent (agent config files, "Co-Authored-By" trailers, AI author credits, agent names in the repo name) from comments, docstrings, filenames, package names, configs, and docs — while leaving code logic byte-for-byte unchanged — then write a Karpathy-style onboarding README. Use this whenever the user says "mystify", "sanitize", "anonymize", "scrub", "de-brand", "clean this repo for GitHub/open source/portfolio", "remove company references", "remove Claude/AI/agent mentions", "hide that this was AI-generated", or wants a repo made publishable. Also use it when asked for a "nanoGPT-style" or "how Karpathy would write it" README for an existing repo.

# Mystify
Turn a repo that was written inside a company into one that could have been written by anyone, without changing what the code does. Then write the README that repo deserves.
The mental model: you are a translator, not an editor. The program is a sentence; you may change the vocabulary (names, comments, docs) but never the grammar (logic, control flow, data). If the tests passed before, they pass after, for the same reasons.
## Non-negotiables
1. **Logic is frozen.** No line that affects runtime behavior changes, except where a rename forces it (an import path after a module rename, a string that *is* the name of a renamed package). If you ever think "while I'm here I could tidy this", stop. That is a different task.
2. **Comments are rewritten, not deleted.** A stripped comment is a lie of omission; a rewritten one should explain the code beneath it to a stranger. The only comments you delete outright are logistical notes with no technical content ("paste this back", "ask Rahul", "check on work laptop").
3. **Renames are total or not at all.** Every rename is applied everywhere (files, dirs, imports, configs, CI, docs, tests) in one batch and verified before the next. A half-applied rename is a broken repo.
4. **Runtime strings are ask-first.** Table names, URLs, hostnames, env var names, queue names, log prefixes: changing them can change behavior. Collect them, propose replacements, and get the user's decision before touching them (see Phase 5).
5. **No coding agent is named anywhere.** Claude, Claude Code, Anthropic, Cursor, Copilot, Codex, Gemini CLI, Aider, Cline, Windsurf, Devin — none appear in the repo name, file names, contributors, commit trailers, comments, or docs after mystify. The repo reads as if a person wrote it.
6. **Nothing is done in place on `main`.** Work on a branch (`mystify/<date>`) so the user can diff and revert.
## What is in scope
| Layer | Examples | Treatment |
|---|---|---|
| Comments & docstrings | `# Lumi MDM tables are ...`, `"""Fetches from EAG ..."""` | Rewrite to describe the code neutrally |
| Logistical notes | `# paste back`, `# TODO check on work laptop`, `# ask Priya` | Delete |
| File / dir / package names | `lumi_extract/`, `amex_utils.py`, `safechain_client.ts` | Rename via mapping, update all references |
| Identifiers derived from those names | `LumiClient`, `EAG_SCHEMA`, `safechainRetry()` | Rename via mapping, same batch as the file rename |
| Project metadata | `pyproject.toml` name, `package.json` name/author/repo URL, `setup.cfg`, `Cargo.toml`, `go.mod` module path | Rename / neutralize |
| Docs | README, `docs/`, ADRs, CHANGELOG, `CLAUDE.md` / `GEMINI.md` | Rewrite affected passages |
| Build & infra | Dockerfiles (internal base images), CI yaml, `.npmrc`/`pip.conf` (internal registries), Makefiles, Helm/Terraform | Neutralize; note anything that cannot run outside the company |
| Notebooks | `.ipynb` markdown cells, cell outputs with internal data | Rewrite markdown; clear outputs that leak names or data |
| Sample data & fixtures | CSV/JSON test fixtures with real-looking internal records | Flag; replace with synthetic only if structure-preserving and tests still pass |
| Agent config & instruction files | `CLAUDE.md`, `.claude/`, `AGENTS.md`, `GEMINI.md`, `.cursor/`, `.cursorrules`, `.windsurfrules`, `.clinerules`, `.github/copilot-instructions.md`, `.aider*`, `.codex/` | Delete (or fold genuinely useful content into `CONTRIBUTING.md` without naming the tool) |
| Agent attribution | `Co-Authored-By: Claude <noreply@anthropic.com>` trailers, "Generated with Claude Code" in PR templates / commit messages, "built with Cursor" in README, agent names in `authors`, `CONTRIBUTORS`, `.mailmap`, `CODEOWNERS`, acknowledgements | Remove; history trailers need Phase 8 |
| Agent-flavored comments | `# Claude: added null check`, `// generated by Copilot`, `# per AGENTS.md rule 3` | Rewrite as an ordinary comment or delete |
| Repo / package name containing an agent | `claude-mdm-extract`, `copilot-utils` | Rename via mapping like any other term |
| Git metadata | remote URLs, author emails in history, `.git/config`, co-author trailers | Report; recommend history reset (Phase 8) |
| Runtime string literals | schema/table names, hostnames, service URLs, env var names, Kafka topics | Ask-first list |
Out of scope: anything that changes an algorithm, a data structure, an API contract, error handling, or formatting of untouched lines.
## Phase 0 — Preconditions
- Confirm `git status` is clean. If not, stop and ask the user to commit or stash.
- Create and check out `mystify/<YYYY-MM-DD>`.
- Establish a baseline: run the test suite (or `python -m compileall .`, `tsc --noEmit`, `go build ./...`, `cargo check`, whichever fits). Record the result in `.mystify/baseline.txt`. If there are no tests, say so explicitly — the diff audit in Phase 6 carries more weight in that case.
- Note the language(s) and package manager(s) so rename mechanics use the right tools (`git mv`, import rewrites, `sed` on lockfiles, etc.).
## Phase 1 — Discover
Run the bundled scanner first; it is faster and more thorough than eyeballing:
```bash
python <skill-dir>/scripts/scan.py . --terms .mystify/terms.txt --out .mystify/scan.md
```
Seed `.mystify/terms.txt` with the terms the user gave you (one per line, case-insensitive). Typical seeds:
```
paste back
work laptop
lumi
american express
amex
eag
safechain
claude
anthropic
copilot
codex
aider
windsurf
cline
devin
co-authored-by
```
Agent terms are always in the seed list, even if the user only mentioned company names — it is part of what mystify means. `cursor` is deliberately not a seed term because it collides with database cursors; the scanner flags `cursor.sh`, `.cursorrules`, `.cursor/`, and "Cursor AI" instead, and you grep `cursor` by hand in docs and comments only.
Also check the places the scanner cannot read as files:
```bash
git log --format='%an <%ae>%n%b' | grep -iE 'claude|anthropic|copilot|codex|co-authored-by|generated (with|by)' | sort | uniq -c
git remote -v
basename "$(git rev-parse --show-toplevel)"   # the repo directory name itself
```
Commit trailers and author lines found here go straight into the Phase 8 history section — they cannot be fixed in the working tree.
The scanner also finds things the user did not list: emails, internal-looking hostnames (`.corp`, `.internal`, `.local`, company domains), Jira-style keys (`ABC-1234`), IP addresses, usernames in paths (`/Users/jdoe/`), and note-style comments (`ask`, `ping`, `paste`, `laptop`, `VPN`, `on-prem`, `prod`). Each hit is tagged by location: `comment`, `string`, `identifier`, `filename`, `doc`, `config`.
Then read the whole repo once, top to bottom, with fresh eyes. The scanner cannot catch "the vendor we use for X" phrased without a keyword, or a comment that only makes sense if you know the company org chart. Add every new term you find to `terms.txt`.
Produce `.mystify/rename-map.json` proposing a neutral, function-derived name for every file, package, and identifier that must change. Good replacement names describe what the thing does, not who owned it:
| Original | Bad replacement | Good replacement |
|---|---|---|
| `lumi_extract/` | `company_extract/` | `catalog_extract/` (it crawls a metadata catalog) |
| `EAGConfig` | `OrgConfig` | `PipelineConfig` |
| `safechain_client.py` | `chain_client.py` | `approval_client.py` (if that is what it talks to) |
If you cannot tell what a thing does well enough to name it, that is a signal to read more code, not to pick a vague name.
**Stop here and show the user** `scan.md` and `rename-map.json`. Ask them to confirm the term list and the mapping. Renames are expensive to redo; a two-minute review now saves an hour later.
## Phase 2 — Rename files, packages, identifiers
Work one mapping entry at a time, largest scope first (package dirs, then modules, then identifiers):
1. `git mv old new` for files and directories (keeps history readable).
2. Update every reference: imports, `__init__.py` re-exports, relative paths in tests, entry points in `pyproject.toml` / `package.json` `main`, Dockerfile `COPY` paths, CI job paths, docs links.
3. For identifiers, use whole-word, case-aware replacement (`LumiClient` → `CatalogClient`, `lumi_client` → `catalog_client`, `LUMI_CLIENT` → `CATALOG_CLIENT`). Never substring-replace: `lumi` inside `illuminate` must survive.
4. Re-run the baseline check from Phase 0. If it fails, fix the rename before moving on — do not accumulate breakage.
5. Commit each batch: `mystify: rename lumi_extract -> catalog_extract`.
Lockfiles (`poetry.lock`, `package-lock.json`, `Cargo.lock`) may embed the old package name; regenerate them with the package manager rather than hand-editing.
## Phase 3 — Rewrite comments and docstrings
For each file, read the code first, then the comments. The comment you write must be true of the code as it is, which you can only know by reading it.
Rules:
- **Same style as the file.** If the file uses terse `#` one-liners, do not introduce paragraphs. If it uses Google-style docstrings, keep Google-style.
- **Explain the why, keep the what short.** `# retry because the upstream API rate-limits bursts` beats `# retry loop`.
- **Preserve technical TODOs, strip logistical ones.** `# TODO: handle pagination past 10k rows` stays. `# TODO: paste back the version from work laptop` goes.
- **Neutralize domain, keep meaning.** `# Lumi returns column lineage as nested JSON` → `# the catalog API returns column lineage as nested JSON`.
- **Docstrings that name the company's systems** get rewritten around the system's role: `"""Client for EAG's approval workflow."""` → `"""Client for the approval-workflow service."""`.
- **Module-level headers** (author lines, copyright with the company name, "Confidential — internal use only") are removed or replaced with the license header the user chooses.
- **Commented-out code** that references internal systems is deleted if clearly dead, otherwise treated like a runtime string (ask-first).
Do not touch blank lines, trailing whitespace, or code lines while you are in this phase. A comment rewrite should produce a diff where every changed line starts with a comment token or sits inside a docstring.
## Phase 4 — Metadata, configs, docs, infra
Go file by file through the non-code surface:
- `pyproject.toml` / `setup.py` / `package.json` / `Cargo.toml` / `go.mod`: name, description, authors, homepage, repository URL, keywords.
- `README.md`, `docs/`, `CHANGELOG.md`, `CONTRIBUTING.md`, ADRs: rewrite affected passages now; the README gets fully rewritten in Phase 7 anyway, so only fix links and names here.
- Dockerfiles: internal base images (`registry.corp/...`) → public equivalents (`python:3.12-slim`); note any that have no public equivalent.
- CI (`.github/workflows`, `.gitlab-ci.yml`, Jenkinsfile): internal runners, secrets names, deploy targets. Replace with a minimal public CI (lint + test) or remove and note it.
- `.npmrc`, `pip.conf`, `.pypirc`, `requirements.txt` with `--index-url`: point at public registries.
- `.env`, `.env.example`, `settings.*`: real values are removed; keys that name internal systems go on the ask-first list.
- `.ipynb`: rewrite markdown cells; `jupyter nbconvert --clear-output` any notebook whose outputs contain internal names or data.
- `LICENSE`, `NOTICE`, `CODEOWNERS`, `.github/CODEOWNERS`: remove owner lists; ask the user which license to apply.
- Agent files: `git rm` `CLAUDE.md`, `AGENTS.md`, `GEMINI.md`, `.claude/`, `.cursor/`, `.cursorrules`, `.windsurfrules`, `.clinerules`, `.github/copilot-instructions.md`, `.aider*`, `.codex/`. If one of them holds real project knowledge (build quirks, test commands, architecture notes), move that content into `CONTRIBUTING.md` or the README first, rewritten so it addresses a human contributor and names no tool. Remove agent entries from `.gitignore` too (`.claude/`, `.cursor/`) — they are a tell.
- `.github/PULL_REQUEST_TEMPLATE.md`, `.github/ISSUE_TEMPLATE/`, `.pre-commit-config.yaml`, `.github/workflows/*`: strip "Generated with Claude Code", `claude-code-action`, Copilot review steps, and any agent-specific job.
- `package.json` `author`/`contributors`, `pyproject.toml` `authors`, `AUTHORS`, `CONTRIBUTORS.md`, `.mailmap`, `humans.txt`: remove any entry that is an agent or a bot (`Claude`, `noreply@anthropic.com`, `copilot[bot]`, `devin-ai-integration`). The user decides what human name, if any, replaces them.
## Phase 5 — Runtime strings and identifiers (ask-first)
Compile every remaining scanner hit tagged `string` into a table:
```
| File:line | Literal | Role (guess) | Proposed replacement | Risk |
|---|---|---|---|---|
| src/extract.py:42 | "lumi_prod.mdm.tables" | BigQuery table id | "catalog.metadata.tables" | changes query target |
| src/config.py:8 | "EAG_API_URL" | env var name | "APPROVAL_API_URL" | breaks existing .env files |
```
Present it and let the user choose per row: replace, keep, or move to config. "Move to config" (hard-coded internal id → `os.environ[...]` with a documented default) is the cleanest outcome for published code but is a logic change, so it only happens on explicit approval and gets its own commit.
## Phase 6 — Verify
Loop until all four pass:
1. **Scanner is silent.** Re-run `scan.py`; zero hits for every term, zero unreviewed pattern hits.
2. **Baseline still passes.** Same test/compile result as Phase 0, for the same reasons.
3. **Diff audit.** `git diff main --stat` then read the full diff. Every changed line must be one of: comment/docstring, a renamed identifier or path, metadata/config, docs, or an approved Phase-5 change. Anything else is a bug — revert it.
4. **Fresh-clone check.** `git clone` the branch into `/tmp`, follow the new README from scratch, confirm the quickstart runs. This is the single most valuable check; it catches the import you forgot and the config you did not document.
5. **Agent sweep.** `grep -rniE 'claude|anthropic|copilot|codex|aider|windsurf|cline|devin|cursorrules|co-authored' --exclude-dir=.git .` returns nothing, and `ls -a` shows no agent dotfiles or dirs.
Also run a secrets scanner if one is available (`gitleaks detect`, `trufflehog filesystem .`). Mystify is not a secrets tool, but it would be embarrassing to publish a clean README next to a live API key.
## Phase 7 — Write the onboarding README
Read `references/readme-template.md` and write `README.md` from it. The target voice is Karpathy's repo READMEs (nanoGPT, llm.c, nanochat): direct, opinionated, no marketing, one command to a working result, an honest "what this is not" section, and a walkthrough of the code in the order a reader should open the files.
The README must be true of the repo *after* mystify: use the new names, the public base images, the neutral terminology. Every command in it must have been run in the fresh-clone check.
## Phase 8 — Report and hand-off
Write `MYSTIFY_REPORT.md` at the repo root:
- Term list used and the final rename map.
- Files touched, grouped by phase, with commit hashes.
- Decisions the user made in Phase 5.
- **Residuals**: anything that still cannot be published as-is (a Dockerfile that needs a base image with no public equivalent, a fixture that is structurally company-specific, a dependency on an internal library).
- **Git history warning**: the working tree is clean but `git log` is not — old names in every diff, `Co-Authored-By: Claude` trailers in commit bodies, agent bots in author lines, the company remote in `.git/config`. Recommend one of:
  - Fresh repo: copy the tree without `.git`, `git init`, one initial commit under the user's own name. Simplest and safest; the only cost is losing history.
  - `git filter-repo --replace-text .mystify/terms.txt --message-callback` to strip trailers and rename terms in place, then re-point the remote. Only if history matters.
  Either way, confirm afterwards with `git log --format='%an <%ae>%n%b' | grep -iE 'claude|anthropic|copilot|co-authored'` returning nothing.
- If the repo directory or GitHub repo name contains an agent or company term, say so explicitly — the user has to rename it on the hosting side; mystify cannot.
- A one-line reminder that mystify removes identifiers, not obligations: the user should still confirm they have the right to publish the code, and that nothing they are publishing to (a license, a platform, a competition) requires disclosing tool use.
## Things that are easy to get wrong
- Substring renames (`lumi` in `illuminate`, `eag` in `eager`, `amex` in `examexample`). Use word boundaries and case variants.
- Renaming a package but not its entry in `pyproject.toml` `[tool.setuptools.packages]` or `package.json` `exports`.
- Rewriting a comment from memory of what the code *should* do instead of what it does. Read the code first.
- Deleting a comment that was the only explanation of a non-obvious constant.
- Leaving old names in test fixture filenames, snapshot files, or `__snapshots__/`.
- Leaving the company name in the LICENSE year line, `CODEOWNERS`, or `.github/ISSUE_TEMPLATE`.
- Assuming a "clean" working tree means a clean repo — the history and the remotes still know where it came from.
- Deleting `CLAUDE.md` but leaving `.claude/` in `.gitignore`, `claude-code-action` in a workflow, or "Generated with Claude Code" in the PR template.
- Substring-matching `cursor` and renaming a database cursor. Check that one by hand.
- Removing the agent from `authors` and leaving the field empty; ask the user what goes there.
